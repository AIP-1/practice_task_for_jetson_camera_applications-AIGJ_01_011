## 1. 카메라 연동과 기준선 (`runs/test_log.md`)

입력 점검 (T0-1, 30초)

| 입력 | 해상도 | 실측 FPS | 첫 프레임 | 끊김 | 프로세스 CPU |
|---|---|---|---|---|---|
| 웹캠 720p | 1280x720 | 30.04 | 0.55 s | 0 | 49.8% |
| 웹캠 1080p | 1920x1080 | 30.02 | 0.46 s | 0 | 62.9% |
| IP stream1 | 2560x1440 | 25.61 | 1.04 s | 0 | 53.7% |
| IP stream2 | 848x480 | 25.73 | 1.24 s | 0 | 8.4% |

지연 측정 (T0-4 리더 방식 × 입력, 처리 0.2 s/장, 2분 / T0-6 glass-to-glass)

| 입력 | (a) `read()` 그대로, 2분 뒤 | (b) 최신 1장 리더, 2분 뒤 | glass-to-glass |
|---|---|---|---|
| 웹캠 720p | 860 ms (0.8 s에서 고정) | 36 ms | 약 180 ms |
| IP 카메라 | 약 105 s (계속 증가) | 1~2 s 이내 | 514 ms (릴레이), 680 ms (원본) |

- 원인: 웹캠 드라이버는 버퍼가 4장뿐이고 넘치면 버린다. 그래서 4장 × 0.2 s ≈ 0.8 s 늦은 상태에서 멈춘다. FFmpeg RTSP는 받은 프레임을 모두 쌓아 두어, 처리(약 3 fps)가 카메라(25 fps)보다 느리면 끝없이 밀린다.
- 조치: 모든 앱에서 (b) 리더(`camlib.LatestReader`)를 쓴다.
- 재연결 (T0-5): 웹캠을 뽑았다 꽂았을 때 33.0 s, IP 카메라 랜선을 뽑았다 꽂았을 때 58 s였다. 읽기 타임아웃을 3 s로 줄인 뒤에는 32 s였다. 둘 다 프로세스는 유지됐다. 기준 30 s를 조금 넘는다. 다시 열기 백오프(최대 8 s)와 RTSP 열기 타임아웃 5 s × 3회가 대부분을 차지한다. 더 줄이려면 백오프 상한을 2 s로 낮춘다.
- 심화 B1 (`runs/b1_decode.md`): 같은 25 fps를 낼 때 NVDEC은 CPU를 1080p에서 0.10코어, 1440p에서 0.15코어만 쓴다. FFmpeg CPU 복원의 1/4~1/5이다.
- 심화 B2 (`runs/b2_rtsp.md`): PC 웹캠을 RTSP로 송출 → MediaMTX → 보드에서 검출했다. 받은 FPS 29.9, 처리 24.9 fps, 프레임 나이 50 ms였다.

## 2. 물체 인식

벤치마크 (`runs/t2_bench.md`, 640, batch 1, coco128 mAP는 비교용)

| 모델 | 추론 평균 / p95 ms | 전체 평균 / p95 ms | FPS 전체 | mAP50-95 | 전력 W | 메모리 MB |
|---|---|---|---|---|---|---|
| PyTorch YOLO11n | 25.2 / 26.8 | 36.0 / 38.0 | 27.8 | 0.508 | 10.0 | 623 |
| TensorRT FP16 | **4.0 / 4.3** | 15.5 / 16.7 | 64 | 0.504 | 10.5 | 553 |
| TensorRT INT8 | 3.3 / 3.5 | 14.6 / 15.9 | 69 | 0.482 | 10.1 | 569 |
| TensorRT YOLO11s FP16 | 6.6 / 7.1 | 20.4 / 22.2 | 49 | 0.576 | 11.7 | 542 |

- INT8은 FP16보다 0.7 ms 빠르지만 mAP가 4.5% 떨어진다. 그래서 기본은 FP16으로 둔다. 보정 데이터가 일반 사진(coco128)이라 현장 프레임으로 다시 보정하면 하락이 줄 수 있다.

조명 × 거리 (`runs/t2_conf.md`, IP 카메라, 사람 1명, 10초): 밝음 2/5/8 m의 conf 평균은 0.929 / 0.894 / 0.887, 어두움은 0.921 / 0.868 / 0.851이다. 6칸 모두 검출률 100%라 이 범위에서는 무너지는 지점이 없다. 어두우면 카메라 FPS가 17~22로 떨어지고 최소 conf가 0.44까지 흔들린다.

선 통과 (`runs/t2_line.md`): ByteTrack + 발 위치 외적, IN 5 / OUT 5 → 센 값 5 / 5, **오차 0**이다. MQTT로 발행했다.

COCO 밖 물품 5종 (`runs/t2_items.md`)

| 방식 | 마이크 | 테이프 | 핸드크림 | 에어팟 케이스 | 쿠션 화장품 | 정답 |
|---|---|---|---|---|---|---|
| ① YOLO | remote | remote | remote | mouse | remote | 0/5 |
| ② 재라벨 (문구만) | remote | remote | ✓ | ✓ | remote | 2/5 |
| ③ YOLOE-11l | ✓ | earbuds case | ✓ | ✓ | ✓ | **4/5** |

- YOLO는 모르는 물체를 모양이 비슷한 COCO 물건(remote, mouse)으로 자신 있게 부른다. 재라벨은 후보 문구에 비슷한 COCO 문구가 있으면 그쪽으로 간다. YOLOE-11s는 2/5였고 11l로 바꾸자 4/5가 됐다. 오인식 스냅샷 14장은 사람이 없는 사진이지만 공개 저장소에서는 이미지를 모두 뺐다.

## 3. 재실 인원 카운터

구성: IP 카메라 stream1 → YOLO11n FP16 **960 + 2x2 조각**(겹침 0.15) → NMS + 포함 억제(0.6) → 발 위치로 구역 판정(`t3/zones/room.json`: include 1, exclude 3, 구역 rear/middle/near) → 최근 **10 s 중앙값** → MQTT retain. 재실 인원 서비스는 과제 6 서비스에 들어가 상시 가동 중이다.

정확도 평가 (`runs/t3_eval_final_output.md`, 2026-10-30 14:43~16:24 기록, 정답 30장, 실제 3~7명)

| 방식 | MAE | 편향 | 정확 | ±1 이내 |
|---|---|---|---|---|
| 프레임 raw | 1.70 | −1.50 | 10% | 37% |
| 로거 count (10 s 중앙값) | 1.77 | −1.63 | 10% | 33% |
| 30 s p75 | **1.40** | −1.13 | 20% | 47% |

- **기준 미달 (❌)**: MAE ≤ 1.0, ±1 ≥ 80%를 어느 방식도 넘지 못했다. 이 평가 묶음에는 빈 방 장면이 없어 빈 방 오판율을 내지 못했다.
- 모든 방식이 적게 센다(편향 −1.1 ~ −1.6). 창을 늘리고 p75로 바꾸면 줄어드는 것으로 보아 프레임마다 가려졌다 보이는 사람(책상·앞사람 가림)이 주된 원인으로 보인다. 다만 사례별로 원인(가림·크기·오검출)을 나눈 분석은 하지 못했다.
- 출입 계수(문 선 `t3_door_1030*`)는 기록했지만, 직접 계수와 30분 동시 운영 비교는 정리하지 못했다.

## 4. 행동 패턴 인식 (웹캠 C920, 1280x720, 사람 1~2명, 2~3 m, 약 15 fps)

| 시험 | raw | 안정화 (0.6 s 다수결) | 판정 |
|---|---|---|---|
| 만세 10 | 10/10, 깜빡임 9 | **10/10, 깜빡임 0** | 합격 |
| 한 팔 들기 10 | 10/10, 깜빡임 0 | 10/10, 깜빡임 0 | 합격 |
| 손 흔들기 10 | - | 10/10 검출 (깜빡임 9: 흔들기 시작·멈춤 순간) | 검출 합격 |
| 한 팔 들고 정지 3 s × 10 | - | 손 흔들기 오판 **0/10** | 합격 |
| 악수 (`runs/t4_handshake.md`) | - | 놓침 1, 나란히 오검출 0 | 합격 |

- 안정화의 반응 지연은 평균 0.31 s다(0.6 s 창의 절반, 이론값과 같다).
- 행동 패턴 (`runs/t4_behavior.md`, 12회 첫 시도): **10/12**(지나가기 2/3, 힐끗 2/3, 관심 3/3, 머무르기 3/3). 틀린 2건은 모두 지나감 ↔ 힐끗 경계(정면 누적 1 s 근처)다.
- 혼동 사례 5건과 원인:
  ① 카메라 쪽으로 걸어오면 관심으로 판정된다(각도).
  ② 폰을 보며 카메라 쪽을 향해 서 있으면 관심으로 판정된다(시선 대신 얼굴 방향).
  ③ 힐끗 1 s가 고개를 돌리는 시간에 묻힌다(창 길이).
  ④ 화면 가장자리에서 돌아서면 정면 1~2 s가 더해진다(각도).
  ⑤ 화면 밖으로 안 나가면 추적이 합쳐진다(설치 구도).
- 설계 변수: 카메라를 통로와 직각으로 돌리자(⑤ 해결) 첫 시도 정답이 크게 올랐다. 직각 구도 전 시도는 8건 중 1건만 맞았다.

  ③ 0.45 m 근접은 +307%였다. 시차 범위를 넓히자 −13%가 됐다.
  ④ 빠른 움직임은 프레임별로 크게 튀었다. 시간 방향 중앙값을 쓰면 −0.4%였다.
- 사람별 거리 (`runs/t5_person_report.md`): 2.7~3.6 m는 ±1.3% 안이었다. 1.35 m는 +5.6~7.0%로 발이 화면 아래에서 잘려 몸통 영역이 위로 치우친다.

## 6. 응용 서비스 — 재실 인원(A1) + 근접 경고(A4)

현장 문제: 강의실 냉난방·환기 제어에는 지금 몇 명이 있는지가 필요하고, 사물함·장비 앞 통로에서는 사람이 너무 가까이 다가오면 알려야 한다. 두 기능을 한 프로세스로 묶었다. TensorRT 엔진 2개가 CUDA 문맥 하나를 같이 쓴다(문맥 하나에 약 0.5 GB라 메모리를 아끼려고). 결과는 MQTT(retain)와 REST로 낸다. 형식은 [interface.md](interface.md)에 있다.
